## Conceptos nuevos

### EF Core frente a JPA

| EF Core | Spring Boot | Qué es |
|---|---|---|
| EF Core | JPA + Hibernate | El ORM |
| Npgsql | Driver JDBC de PostgreSQL | El conector con la base de datos |
| Clase normal (POCO) | `@Entity` | Una tabla |
| `DbContext` | `EntityManager` + los `JpaRepository` | La sesión con la base de datos |
| `DbSet<Product>` | `JpaRepository<Product, Long>` | Una tabla consultable con LINQ |
| Migraciones de EF Core | Flyway / Liquibase | Versionado del esquema |
| `dotnet ef database update` | `mvn flyway:migrate` | Aplicar las migraciones pendientes |
| `__EFMigrationsHistory` | `flyway_schema_history` | Registro de migraciones aplicadas |

### Entidades por convención

La entidad `Product` no tiene ninguna anotación. EF Core deduce el mapeo por convención:

- Una propiedad `Id` de tipo `int` es la clave primaria autoincremental (`GENERATED BY DEFAULT AS IDENTITY`).
- Un tipo **no anulable** (`string`, `int`, `decimal`) genera una columna `NOT NULL`; uno anulable (`string?`, `int?`) la permite nula. Funciona con `string` porque el proyecto tiene `<Nullable>enable</Nullable>`.

### Propiedades, `required` y *object initializers*

```csharp
public required string Name { get; set; }
```

- `{ get; set; }` es una **propiedad**: getter y setter en una línea, como lo que genera Lombok con `@Getter @Setter`, pero integrado en el lenguaje.
- `required` obliga a asignarla al crear el objeto. `new Product { Brand = "Apple" }` no compila porque falta `Name`.
- `new() { Name = "...", Brand = "..." }` es un *object initializer*: crea el objeto y asigna propiedades en una expresión. Se parece al *builder* de Lombok.

### Fluent API

El mapeo que en JPA irían en anotaciones se escribe en una clase aparte que implementa `IEntityTypeConfiguration<Product>`:

| Fluent API | JPA |
|---|---|
| `.HasMaxLength(200)` | `@Column(length = 200)` |
| `.HasConversion<string>()` | `@Enumerated(EnumType.STRING)` |
| `.HasPrecision(10, 2)` | `@Column(precision = 10, scale = 2)` |
| `.HasIndex(p => p.Category)` | `@Table(indexes = @Index(columnList = "category"))` |

Así la entidad no depende de EF Core. `ApplyConfigurationsFromAssembly` en el `DbContext` registra todas las configuraciones del proyecto automáticamente.

### Registro del `DbContext` y su ciclo de vida

```csharp
builder.Services.AddDbContext<AppDbContext>(options =>
    options.UseNpgsql(connectionString).UseSnakeCaseNamingConvention());
```

`AddDbContext` lo registra como **scoped**: **una instancia por petición HTTP**, igual que el `EntityManager` de Spring en una petición web. Un `DbContext` no es *thread-safe* y no se comparte entre peticiones.

### Cadenas de conexión

```json
"ConnectionStrings": {
  "Default": "Host=localhost;Port=5433;Database=docassist;Username=docassist;Password=docassist_dev"
}
```

Se leen con `builder.Configuration.GetConnectionString("Default")`. Es el `spring.datasource.*` de Spring, pero en una sola cadena. En producción llega por la variable de entorno `ConnectionStrings__Default`.

### Liveness frente a readiness

| Endpoint | Pregunta | Si falla, el orquestador... | Mira la BD |
|---|---|---|---|
| `/health` | ¿El proceso está vivo? | Reinicia el contenedor | No |
| `/health/ready` | ¿Puede atender peticiones? | Le quita el tráfico hasta que se recupere | Sí |

Si la base de datos se cae, reiniciar la API no arregla nada. Por eso la comprobación de la base va solo en *readiness*. Se separa con **etiquetas**: el *check* lleva `tags: ["ready"]` y cada endpoint filtra con un `Predicate`. Es lo mismo que `/actuator/health/liveness` y `/actuator/health/readiness` de Spring Boot.

### Migraciones generadas

A diferencia de Flyway, **no se escribe el SQL**: EF Core compara el modelo actual con el *snapshot* anterior y genera la migración. Cada migración produce tres archivos:

| Archivo | Qué es | ¿Se edita? |
|---|---|---|
| `<fecha>_InitialCreate.cs` | La migración: `Up()` aplica, `Down()` deshace | Sí, si hace falta (por ejemplo, `migrationBuilder.Sql(...)`) |
| `<fecha>_InitialCreate.Designer.cs` | Cómo era el modelo en esta migración | Nunca |
| `AppDbContextModelSnapshot.cs` | Cómo es el modelo ahora; se usa para calcular la siguiente migración | Nunca |

- **`Down()`** permite deshacer, algo que Flyway Community no incluye.
- El **snapshot** se sube a git siempre. Es el archivo que da conflictos cuando dos ramas generan migraciones a la vez.
- **`dotnet ef migrations script`** muestra el SQL sin tocar la base de datos: la mejor forma de revisar una migración generada.

### Seed: `HasData` frente a `UseSeeding`

| | `HasData` | `UseSeeding` / `UseAsyncSeeding` |
|---|---|---|
| Dónde vive | Dentro de las migraciones, como `INSERT` | Código que se ejecuta después de migrar |
| Para qué | Datos de referencia del esquema (países, tipos de IVA) | Datos de ejemplo o iniciales |
| Ids | Fijos, a mano | Los genera la base de datos |
| Llega a producción | Siempre | Solo si se quiere |
| En Spring | Un `V2__datos.sql` de Flyway | Un `CommandLineRunner` o `data.sql` con perfil `dev` |

Usamos `UseSeeding` porque son datos de demostración y no deben llegar a producción. Se registra solo si el entorno es `Development`. Es **idempotente**: si ya hay productos, no inserta nada. Hay versión síncrona (la usa `dotnet ef database update`) y asíncrona (la usará la app al migrar desde código).

### Herramientas locales de .NET

`dotnet new tool-manifest` + `dotnet tool install dotnet-ef` fija la versión de la herramienta en `.config/dotnet-tools.json`. Quien clone el repo ejecuta `dotnet tool restore` y tiene exactamente la misma versión. Es la idea del `mvnw` de Maven.

### Dependencias solo de desarrollo

El paquete `Microsoft.EntityFrameworkCore.Design` tiene `<PrivateAssets>all</PrivateAssets>`: lo necesita `dotnet ef` para generar migraciones, pero no se propaga a otros proyectos. Es el `<scope>provided</scope>` de Maven o las `devDependencies` de npm.

## Cómo probarlo

**Preparar la base de datos** (con Docker Desktop arrancado):

```powershell
cd C:\dev\PERSONAL\proyecto-C#-Angular
docker compose up -d

cd backend
dotnet tool restore                                   # instala dotnet-ef desde el manifiesto
dotnet ef database update --project src/DocAssist.Api # crea la tabla e inserta los productos
```

La primera vez que se aplica sobre una base vacía aparece un `fail` al consultar `__EFMigrationsHistory`. Es esperado: la tabla aún no existe, EF Core captura el error, la crea y sigue. Lo importante es que termine en `Done.`

**Ver el SQL de la migración sin aplicarla:**

```powershell
dotnet ef migrations script --project src/DocAssist.Api
```

**Consultar los datos:**

```powershell
cd C:\dev\PERSONAL\proyecto-C#-Angular
docker compose exec db psql -U docassist -d docassist
```

```sql
\dt
\d products
SELECT * FROM "__EFMigrationsHistory";
SELECT id, name, category, price, stock, ram_gb, screen_inches FROM products ORDER BY category, price;

-- La pregunta de ejemplo: móviles de menos de 500 € con al menos 8 GB de RAM
SELECT name, price, ram_gb FROM products
WHERE category = 'Phone' AND price < 500 AND ram_gb >= 8;   -- Redmi Note 14 Pro
\q
```

Si una consulta abre el paginador (`(END)` abajo), se sale con `q`. Con `\pset pager off` se desactiva.

**Comprobar la idempotencia del *seed*:** volver a ejecutar `dotnet ef database update` y comprobar que `SELECT count(*) FROM products;` sigue en 10.

**Probar liveness y readiness:**

```powershell
cd C:\dev\PERSONAL\proyecto-C#-Angular\backend
dotnet run --project src/DocAssist.Api

# en otro terminal
curl http://localhost:5080/health          # Healthy
curl http://localhost:5080/health/ready    # Healthy

docker compose stop db
curl http://localhost:5080/health          # Healthy (el proceso sigue vivo)
curl -i http://localhost:5080/health/ready # 503 Unhealthy

docker compose start db
curl http://localhost:5080/health/ready    # Healthy otra vez, sin reiniciar la API
```

**Tests:** `dotnet test` desde `backend/` (3 tests; ninguno usa la base de datos todavía).

**Empezar de cero con la base de datos** (sin tocar los modelos de Ollama):

```powershell
cd C:\dev\PERSONAL\proyecto-C#-Angular\backend
dotnet ef database drop --project src/DocAssist.Api --force   # borra la base docassist
dotnet ef database update --project src/DocAssist.Api         # la recrea con la migración y el seed
```

Evita `docker compose down -v` para esto: borra todos los volúmenes, incluidos los ~5 GB de modelos de Ollama.

## Decisiones y alternativas

| Decisión | Por qué | Alternativas |
|---|---|---|
| Fluent API en clases `IEntityTypeConfiguration` | La entidad no depende de EF Core y cada mapeo está en su archivo | Atributos (`[MaxLength]`, `[Precision]`) en la entidad, más parecidos a JPA |
| `DbContext` sin repositorios encima | `DbSet` ya es un repositorio y `DbContext` una unidad de trabajo; otra capa solo reenviaría llamadas | Un `ProductRepository` por entidad, como en Spring. Tiene sentido si se quiere aislar el dominio de EF Core |
| `snake_case` con `EFCore.NamingConventions` | Nombres idiomáticos en Postgres, sin comillas en cada consulta | Nombres por defecto en PascalCase entre comillas (`"Products"`, `"ReleaseDate"`) |
| Enum guardado como texto | Legible en la base y no se rompe si se reordena el enum | Guardar el número (por defecto) |
| `Id` entero autoincremental | Simple y legible para aprender y para las consultas del agente | `Guid` (v7): mejor si los ids se generan en varios sitios o no deben ser adivinables |
| `UseSeeding` solo en desarrollo | Son datos de demostración; no deben llegar a producción ni generar migraciones al cambiar un precio | `HasData`, que los metería en la migración |
| Cadena de conexión en `appsettings.Development.json` | La contraseña es la del contenedor local y ya estaba en `docker-compose.yml`; en otros entornos llega por variable de entorno | `dotnet user-secrets`: fuera del repo, pero cada persona que clona lo tiene que configurar |
| Liveness sin base de datos, readiness con base de datos | Una caída de la base no debe provocar reinicios en cadena de la API | Un solo `/health` que lo comprueba todo |
| Migraciones aplicadas con `dotnet ef database update` | Es explícito: se ve cuándo y qué se aplica | `Database.MigrateAsync()` al arrancar la app: cómodo en desarrollo y en contenedores, pero arriesgado con varias instancias en producción. Se valorará en el paso 12 |
| `dotnet-ef` como herramienta local | Versión fijada en el repo, igual para todos y en CI | Herramienta global (`dotnet tool install -g`): cada máquina puede tener una versión distinta |
| Sin tests contra la base de datos en este paso | Aún no hay código nuestro que use la base; se probaría EF Core, no el proyecto | Se añadirán en el paso 4 con Testcontainers, junto con el CRUD |

## Para la entrevista

**Frases que puedo decir:**

> "Uso EF Core con Npgsql y la Fluent API en clases de configuración separadas, así las entidades no dependen del ORM. Las migraciones las genera EF Core comparando el modelo con el *snapshot*, pero siempre reviso el SQL con `dotnet ef migrations script` antes de aplicarlas."

> "Separé *liveness* y *readiness*: `/health` solo dice si el proceso está vivo y `/health/ready` comprueba la base de datos. Si Postgres se cae, la API deja de recibir tráfico pero no se reinicia en bucle, y se recupera sola cuando vuelve la base."

> "Los datos de ejemplo van con `UseSeeding` y no con `HasData`, porque son de demostración: se registran solo en desarrollo y no acaban dentro de las migraciones de producción."

**Posibles preguntas:**

- *¿Qué diferencia hay entre las migraciones de EF Core y Flyway?*
  En Flyway escribes el SQL a mano. EF Core compara el modelo con el *snapshot* y genera la migración en C#, con `Up` y `Down`. Hay que revisarla igualmente, y se puede editar para añadir SQL propio.

- *¿Para qué sirve el `ModelSnapshot`?*
  Es la foto del modelo tras la última migración. EF Core lo compara con las entidades actuales para calcular la siguiente migración. Se versiona siempre y no se edita a mano.

- *¿Qué pasa si dos desarrolladores crean migraciones en ramas distintas?*
  Al fusionar, el *snapshot* tiene conflicto y las dos migraciones no se conocen entre sí. Lo habitual es que uno de los dos elimine la suya, fusione y la vuelva a generar encima de la del otro.

- *¿Usarías repositorios con EF Core?*
  Normalmente no: `DbContext` ya es una unidad de trabajo y `DbSet` un repositorio. Añadir otra capa suele ser reenviar llamadas. Lo consideraría si quisiera aislar el dominio de EF Core o si hubiera consultas complejas que reutilizar en muchos sitios.

- *¿Qué ciclo de vida tiene un `DbContext`?*
  *Scoped*: uno por petición. No es *thread-safe*, así que no se comparte entre peticiones ni entre hilos.

- *¿`HasData` o `UseSeeding`?*
  `HasData` para datos de referencia que forman parte del esquema, porque van dentro de la migración. `UseSeeding` para datos iniciales o de ejemplo, que se pueden limitar a un entorno y cambiar sin generar migraciones.

- *¿Por qué separar liveness y readiness?*
  Porque piden acciones distintas. Si falla *liveness*, se reinicia el proceso; si falla *readiness*, solo se deja de enviarle tráfico. Si una dependencia externa como la base de datos se cae, reiniciar no ayuda, así que va en *readiness*.
